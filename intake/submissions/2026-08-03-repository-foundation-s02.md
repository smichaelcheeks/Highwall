# Verbatim Highwall Repository Initialization

## Author instruction

Establish a clean, scalable repository structure for Highwall without inventing or adding setting lore. Treat long-term maintainability and safe human/AI collaboration as higher priorities than completeness.

## Submitted information

The following seed document is preserved verbatim from the author's original submission.

> # Highwall Repository Initialization
>
> This repository will become the canonical source of truth for my original fantasy setting, **Highwall**. It will eventually function as both an author reference and a wiki, with AI assisting in maintaining consistency over time.
>
> The repository is currently empty. Your first responsibility is **not** to invent lore or write worldbuilding. Instead, establish a clean, scalable structure that future work can build upon.
>
> ## Project Goals
>
> This repository should serve several purposes simultaneously:
>
> - A canonical encyclopedia for the setting.
> - A reference while writing novels.
> - A searchable knowledge base.
> - A system for detecting contradictions.
> - A repository that AI can safely update without unintentionally changing canon.
>
> Long-term maintainability is more important than completeness.
>
> ---
>
> # Design Philosophy
>
> Treat this repository like documentation for a large software project rather than a collection of notes.
>
> Every fact should have a single authoritative location.
>
> Pages should reference one another instead of duplicating information.
>
> The repository should distinguish between:
>
> - established canon
> - working canon
> - unresolved ideas
> - discarded ideas
> - story structure
> - historical truth
> - in-world beliefs
>
> Never assume these are the same thing.
>
> ---
>
> # Canon Rules
>
> Assume that nothing is canon unless explicitly documented.
>
> Never invent lore.
>
> Never fill gaps creatively unless explicitly instructed.
>
> When uncertain, create placeholders or TODO sections rather than guessing.
>
> If conflicting information appears later, do not silently choose one version.
>
> Instead:
>
> - identify the contradiction
> - document both possibilities
> - explain where each appears
> - wait for a decision
>
> ---
>
> # Repository Organization
>
> Create a scalable directory structure intended to support a large fictional universe.
>
> At minimum include areas similar to:
>
> - canon
> - story
> - development
> - references
> - templates
>
> Within canon, anticipate categories such as:
>
> - characters
> - places
> - institutions
> - history
> - government
> - religion
> - economy
> - technology
> - culture
> - law
> - terminology
>
> Do not populate these with invented content.
>
> ---
>
> # Canon vs Story
>
> Keep world information separate from story information.
>
> For example:
>
> A country's history belongs in canon.
>
> A novel chapter belongs in story.
>
> Character knowledge belongs in story.
>
> Actual historical truth belongs in canon.
>
> Reader reveals belong in story.
>
> Do not merge these concepts.
>
> ---
>
> # Development Area
>
> Create a development section intended for material that is still evolving.
>
> This area should support things like:
>
> - open questions
> - proposals
> - contradiction reports
> - decision records
> - retired ideas
>
> This is where brainstorming belongs.
>
> It is intentionally separate from canon.
>
> ---
>
> # Markdown Standards
>
> Use plain Markdown.
>
> Prefer relative links between documents.
>
> Design the repository so it could later be used by systems like MkDocs, Quartz, Obsidian, Docusaurus, or similar static wiki generators.
>
> Do not depend on any specific documentation framework.
>
> ---
>
> # Front Matter
>
> All canon pages should be designed to support YAML front matter.
>
> Suggested metadata includes fields such as:
>
> - title
> - type
> - status
> - canon_level
> - aliases
> - tags
> - related
>
> These fields may evolve over time.
>
> ---
>
> # Templates
>
> Create reusable templates for at least:
>
> - character
> - place
> - institution
> - historical event
> - culture
> - government office
> - organization
> - technology
> - decision record
> - open question
>
> Templates should emphasize structure rather than content.
>
> ---
>
> # README
>
> Replace the temporary README with a professional project overview describing:
>
> - the purpose of the repository
> - its organizational philosophy
> - how canon is managed
> - the distinction between canon and development
> - how contributors (human or AI) should work within the repository
>
> ---
>
> # CONTRIBUTING
>
> Create a CONTRIBUTING.md describing the working rules for future AI collaboration.
>
> It should include principles such as:
>
> - Never invent canon.
> - Never silently resolve contradictions.
> - Prefer links over duplicated explanations.
> - Keep brainstorming out of canon.
> - Record significant canon changes.
> - Preserve narrative ambiguity when instructed.
> - Ask for clarification rather than guessing.
>
> ---
>
> # Initial Commit
>
> For this first task:
>
> 1. Build the repository structure.
> 2. Create the templates.
> 3. Replace the README.
> 4. Create CONTRIBUTING.md.
> 5. Add any additional documentation that establishes repository standards.
>
> Do not add Highwall lore yet.
>
> When finished, summarize the structure you created and explain any design decisions before making further changes.
